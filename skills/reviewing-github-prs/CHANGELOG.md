  - `debate-review`

### 1. Base State (A)
- Supported PR metadata viewing, diff analysis, 4-scale review taxonomy, local verification, and `gh api` submission.
- Did not distinguish issue-level comments from inline review threads or document fetching review discussion via API.
- Lacked commands for inspecting CI checks and failure logs directly from the CLI.
- Did not warn about the security risks of checking out and running build/test scripts on untrusted external PRs.
- Did not document deterministic `commit_id` binding or multi-line comment spans in review payloads.

### 2. Curated Changes Applied (A -> B)
- **Step 1 (Inspect PR Context, Scope & Linked Issues)**:
  - Clarified that `gh pr view --comments` only returns issue-level conversation comments, not inline review threads.
  - Added `gh api repos/{owner}/{repo}/pulls/<pr-number>/comments` command to fetch existing inline review comment threads.
  - Added CI check inspection commands (`gh pr checks <pr-number-or-url>` and `gh run view <run-id> --log-failed`).
- **Step 2 (Fetch and Analyze the PR Diff)**:
  - Added requirement to inspect removed/weakened guards (`-` lines) via `git log -S` or `git blame`.
- **Step 3 (Local Checkout & Empirical Verification)**:
  - Added `[!WARNING]` on untrusted PR checkouts: inspect build scripts, `Makefile`, `package.json`, and workflow diffs before executing test suites.
- **Step 5 (Draft and Submit Review via GitHub API)**:
  - Added `commit_id` field to review JSON payload to deterministically bind reviews to `headRefOid`.
  - Documented `start_line` and `start_side` syntax for multi-line comment spans.
- Bumped version metadata to `1.4`.

### 3. Resulting State (B)
- A more resilient and secure PR review workflow with complete comment visibility, CI failure inspection, untrusted code execution guards, and deterministic GitHub API review submission.

## [2026-10-19] - Clean Review Bodies: Omit Redundant Summary Headings and Empty Sections

### 1. Motivation
- Eliminate unnecessary visual clutter and placeholder noise in PR reviews submitted to GitHub.
- Avoid rendering empty sections with boilerplate text (such as `### Comments on Lines Outside Diff` with `(none)` or `*(None)*`).
- Streamline GitHub review summaries by starting directly with the summary text, omitting redundant top-level `Summary` or `Executive Summary` headers since the GitHub PR review comment UI already provides clear context.

### 2. Curated Changes Applied
- **Step 4 (Partition Findings into Inline Comments & Summary Body)**:
  - Instructed agents to omit leading `# Summary`, `## Summary`, `### Summary`, or `### Executive Summary` headings when formatting for GitHub review submission and begin directly with the summary text.
  - Mandated that agents completely eliminate empty sections rather than printing placeholders like `(none)`, `*(None)*`, or `N/A`.
  - Clarified that `### Comments on Lines Outside Diff` is conditional and must only appear if there are actual displaced findings on unmodified lines outside the diff hunks.
- **Step 5 (Draft and Submit Review via GitHub API)**:
  - Updated example review JSON payload to omit `### Executive Summary` and eliminate the empty `### Comments on Lines Outside Diff\n*(None)*` block.
  - Updated HTTP 422 remediation instructions to note that `### Comments on Lines Outside Diff` is created dynamically only when comments are displaced.
- **PR Review Etiquette**:
  - Added etiquette rule 6 to omit empty sections and redundant summary headings.
- Bumped version metadata to `1.3`.

### 3. Resulting State
- PR reviews posted to GitHub are concise and clutter-free: reviews jump directly into the summary evaluation and contain only sections with meaningful, actionable content.

## [2026-10-18] - Trailing AI Generation Disclosure on GitHub Review Submission

### 1. Motivation
- Provide transparent provenance on pull request reviews submitted to GitHub.
- Clearly disclose to PR authors and maintainers which agent harness and model generated the review feedback.

### 2. Curated Changes Applied
- **Step 4 (Partition Findings into Inline Comments & Summary Body)**:
  - Added requirement for a trailing generation disclosure in italics (`*Generated by <agent harness> using model <model>*`) in the review summary body when submitting reviews to GitHub.
  - Specified that this disclosure should only appear when submitting the review to GitHub (omitted from local review sessions or scratch notes).
- **Step 5 (Draft and Submit Review via GitHub API)**:
  - Updated the JSON review payload example to illustrate the trailing `*Generated by <agent harness> using model <model>*` message in the `body`.
- **PR Review Etiquette**:
  - Added etiquette rule 5 mandating the trailing AI generation disclosure whenever submitting reviews to GitHub via `gh api`.
- Bumped version metadata to `1.2`.

### 3. Resulting State
- Reviews submitted to GitHub cleanly disclose their automated origin and model provenance at the end of the summary body while maintaining all multi-scale review and diff-verification guarantees.

## [2026-10-14] - Inline Comments via GitHub API & Curation from le-skills

- **Upstream Repository**: `https://github.com/learningequality/le-skills.git`
- **Upstream Revision**: `9dc3e40713b25f74509e01847cf80e6582421d70`, committed on 2026-08-01 (tag: `v26.08.01.1`)
- **Upstream Source Path**: `sources/le-skills/skills/github-pr-review/`

### 1. Base State (A)
- Upstream `github-pr-review` in `le-skills` provided a 5-phase PR review protocol with visual inspection, manual QA, terse writing gates, delta reviews, and submission of reviews with inline comments using `gh api repos/{owner}/{repo}/pulls/{pr_number}/reviews`.
- Handled diff line verification against hunk headers (`[ns, ns+nc-1]` for `RIGHT`, `[os, os+oc-1]` for `LEFT`) and displaced out-of-hunk findings to review body to avoid HTTP 422 errors.
- Handled pending review creation (omitting `event`) vs. autonomous publishing (`REQUEST_CHANGES`, `COMMENT`, `APPROVE`).

### 2. Curated Changes Applied (A -> B)
- **Renamed**: `github-pr-review` → `reviewing-github-prs` to adhere to repository gerund authoring conventions (`reviewing-code`, `executing-plans`, `writing-specs`).
- **Standardized Metadata**:
  - Configured repository-standard YAML frontmatter in `SKILL.md`: `license: MIT`, `user-invocable: true`, `compatibility`, `allowed-tools`, and `metadata`.
- **Integrated Multi-Scale Engineering Taxonomy**:
  - Replaced upstream terse-writing gate and bespoke severity labels with this repository's 4-scale software engineering review philosophy (`engineering-software` and `reviewing-code`) and standard 4-tier finding taxonomy (`🚨 Blocker (Must-Fix)`, `⚠️ Architecture & Design (Should-Fix)`, `💡 Tactical Suggestion (Optional)`, `✅ Positive Highlights`).
- **Inline Comment Drafting & Diff Hunk Verification**:
  - Replaced single-comment `gh pr review --body-file` submission with structured inline comment drafting via `gh api repos/{owner}/{repo}/pulls/<pr-number>/reviews`.
  - Added strict diff hunk verification using `gh pr diff <pr-number> -- <file>` to ensure comment lines fall within hunk bounds (`side: "RIGHT"` / `side: "LEFT"`).
  - Adopted out-of-hunk displacement pattern: automatically shift findings on unmodified lines into a dedicated `### Comments on Lines Outside Diff` section in the review summary body, preventing HTTP 422 API errors.
  - Standardized JSON input drafting via `--input <payload.json>` to eliminate shell escaping issues with complex multi-line Markdown and code diffs.
  - Maintained default pending review workflow (omitting `event` for human inspection via "Finish your review") while documenting autonomous submission (`REQUEST_CHANGES`, `COMMENT`, `APPROVE`).

### 3. Resulting State (B)
- A comprehensive GitHub Pull Request review skill combining multi-scale architectural analysis with battle-tested GitHub API inline diff comment submission, hunk verification, pending review staging, and HTTP 422 resilience.
